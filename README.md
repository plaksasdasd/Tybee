# Тайби — Telegram-бот доставки японских товаров

Современный Telegram-бот сервиса **Тайби** для доставки товаров из Японии.
Построен на **aiogram 3** + **PostgreSQL** (SQLAlchemy async), упакован в **Docker**.

## Ключевая особенность: сообщения редактируются, а не удаляются

Бот держит для каждого пользователя **одно «экранное» сообщение** и при навигации
**редактирует** его (баннер + текст + кнопки) вместо удаления и отправки нового.
Чат остаётся чистым, история не засоряется. Логика — в
[`app/services/navigation.py`](app/services/navigation.py).

## Возможности

- `/start` — главное меню (баннер приветствия).
- **Оформить заказ**: выбор способа — по артикулу / Mystery Box / персональная
  заявка.
- **По артикулу**: ввод 6-значного кода с сайта tybee.ru → поиск в каталоге →
  - найдено → одобрение → оплата по реквизитам → «Я оплатил» → проверка оплаты
    администратором → одобрение/отклонение → диалог с командой;
  - не найдено → предложение оформить персональную заявку.
- **Mystery Box**: клиент выбирает готовый бокс-сюрприз из списка (типы боксов
  заводятся через `/admin`) → счёт выставляется сразу → после оплаты диалог с
  командой. Если боксов нет — предложение оформить персональную заявку.
- **Персональная заявка**: описание заказа → диалог с командой.
- **Личный кабинет**: список заказов и публичная оферта.
- **Поддержка / диалог с командой**: сообщения пользователя ретранслируются в
  чат поддержки; ответ администратора (reply) возвращается пользователю.
- **Ветки клиентов**: если `SUPPORT_CHAT_ID` — форум-супергруппа (включены темы),
  для каждого клиента автоматически создаётся одна общая тема (ветка). Туда
  публикуются все платежи, заказы и сообщения клиента, и **любое текстовое
  сообщение саппорта в ветке уходит клиенту**.
- **Интеграция с Авито** (опционально): сообщения клиентов из Авито
  (Messenger API, вебхуки) приходят в отдельную ветку на каждого клиента.
  Саппорт отвечает обычным сообщением в ветке, выставляет счёт `/order` и меняет
  статус заказа кнопками — всё уходит клиенту в Авито. Кнопки подтверждения
  оплаты приходят в ветку сразу после выставления счёта (у Авито-клиента нет
  кнопки «Я оплатил» — саппорт подтверждает вручную, когда клиент напишет об
  оплаты). Настройка: включите тумблер `AVITO_ENABLED=true` и заполните
  `AVITO_CLIENT_ID`, `AVITO_CLIENT_SECRET` (приложение на dev.avito.ru),
  `AVITO_WEBHOOK_URL` (публичный HTTPS-адрес сервера), `AVITO_WEBHOOK_SECRET`,
  `AVITO_WEBHOOK_PORT`.
- **Команды саппорта** (в ветке клиента или ответом на его сообщение):
  - `/order [название] [описание] [сумма]` — выставить счёт: клиенту приходит
    уведомление с суммой и реквизитами и кнопкой «Я оплатил»;
  - `/ban [id или @username]` — заблокировать клиента (для разблокировки клиент
    платит штраф в Telegram Stars ⭐). Можно вызвать ответом на сообщение клиента
    или в его ветке (без аргумента), либо указать `id`/`@username` явно — в т.ч.
    в личке администратора;
  - `/pardon [id или @username]` — разблокировать клиента (те же способы указания
    цели).
- **Админ-панель** `/admin` (в личке администратора): управление каталогом —
  добавление товара (`артикул название цена`), включение/снятие с продажи,
  удаление; управление **Mystery Box** — добавление бокса (`название цена`),
  включение/выключение, удаление; а также статистика (пользователи, баны,
  товары, боксы, заказы по статусам).
- **Статусы заказа**: после подтверждения оплаты в общей ветке клиента появляются
  кнопки смены статуса (Принят, Выкуплен, Доставляется в Россию, На таможне,
  Доставляется по России, Ожидает получения, Получен). Каждая смена статуса
  сопровождается уведомлением клиенту.
- **Админ**: подтверждение/отклонение оплаты по кнопкам, уведомления о новых
  заявках, двусторонняя переписка с клиентом.

Все баннеры лежат в [`assets/banners/`](assets/banners) и привязаны к
соответствующим экранам в [`app/assets.py`](app/assets.py). Каждый экран —
это фото-сообщение (баннер + подпись HTML + клавиатура), которое
редактируется на месте через `edit_message_media`, поэтому история чата
остаётся чистой и баннер не «пропадает» при переходах. Новый баннер
загружается один раз, его `file_id` кэшируется в БД и переиспользуется.
Логика — в [`app/services/navigation.py`](app/services/navigation.py).

## Запуск (Docker)

1. Создайте `.env` на основе примера и впишите токен бота от
   [@BotFather](https://t.me/BotFather):

   ```bash
   cp .env.example .env
   # отредактируйте BOT_TOKEN и ADMIN_IDS
   ```

   - `BOT_TOKEN` — токен бота.
   - `ADMIN_IDS` — Telegram ID администраторов через запятую (например `12345,67890`).
   - `SUPPORT_CHAT_ID` — (опционально) ID группы поддержки. Если пусто, диалоги
     идут первому администратору из `ADMIN_IDS`. Чтобы получать сообщения в группе,
     добавьте туда бота и отключите ему privacy mode в @BotFather.

2. Поднимите стек (бот + PostgreSQL):

   ```bash
   docker compose up --build
   ```

   Бот применит схему БД и засеет демо-каталог автоматически при старте.

## Запуск без Docker (для разработки)

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
# поднимите Postgres (например docker compose up -d db) и задайте POSTGRES_HOST=localhost
export $(grep -v '^#' .env | xargs) && export POSTGRES_HOST=localhost
python -m app
```

## CI/CD

В репозитории есть workflow `.github/workflows/ci-cd.yml`, который:

- собирает код и Docker-образ на `push` в `main`;
- умеет вручную запускать бота на тестовый интервал до 6 часов
  (`workflow_dispatch`).

Для ручного запуска нужны secrets:

- `BOT_TOKEN`
- `ADMIN_IDS`
- `SUPPORT_CHAT_ID` — опционально

Во время тестового запуска workflow поднимает PostgreSQL service и стартует бот
через `python -m app`.

## Структура

```
app/
├── __main__.py          # точка входа (python -m app)
├── bot.py               # сборка Bot/Dispatcher, polling
├── config.py            # настройки из .env (pydantic-settings)
├── middlewares.py       # сессия БД + загрузка пользователя на каждый апдейт
├── assets.py            # перечень баннеров
├── texts.py             # все тексты (RU)
├── states.py            # состояния диалога пользователя
├── db/                  # модели, движок, сидинг
├── repositories/        # доступ к данным
├── services/            # navigation (edit-not-delete), notify (relay), screens
├── keyboards/           # inline-клавиатуры
└── handlers/            # хендлеры flow (start, profile, article, payment, …)
```
